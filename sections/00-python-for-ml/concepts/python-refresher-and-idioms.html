1Why can editing one list quietly wreck another?

Suppose you store four quiz scores in baseline = [72, 81, 68, 90], then write trial = baseline to test a bonus run. You set trial[0] = 95 and call trial.append(88). When you print baseline to compare, your "untouched" original has quietly turned into [95, 81, 68, 90, 88].

No error fired, yet your original data changed. Keep one physical picture across this chapter: a Python list is a cardboard box holding ordered items, and a variable name is a sticky note stuck onto a box.

Writing trial = baseline never copies the box — it sticks a second label onto the same box (called aliasing), so edits through trial rewrite baseline too:

baseline = [72, 81, 68, 90]
trial = baseline          # two sticky notes, same box

trial[0] = 95
trial.append(88)

print("trial:   ", trial)     # [95, 81, 68, 90, 88]
print("baseline:", baseline)  # [95, 81, 68, 90, 88]

To keep baseline intact, build a fresh box with a slice copy (baseline[:]) or list(baseline) before editing:

baseline = [72, 81, 68, 90]
trial = baseline[:]       # new box with copied values

trial[0] = 95
trial.append(88)

print("trial:   ", trial)     # [95, 81, 68, 90, 88]
print("baseline:", baseline)  # [72, 81, 68, 90]

Compare two sticky notes on one box (b = a) against a separate slice copy (sub = list(xs[1:4]), whose [1:4] slice rule comes next in Section 2):

Top: b = a puts two labels on the same box, so editing b[0] changes a. Bottom: slicing into list(xs[1:4]) (or copying with a[:]) creates a separate box so xs stays untouched.
Where this analogy breaks: Boxes work well for flat lists of numbers or strings, with two limits. First, immutable values (numbers, strings, tuples) cannot be edited in place — x = x + 1 moves the sticky note onto a new box. Second, for nested lists (boxes inside boxes), a[:] builds a new outer box that still shares its inner boxes — a 2D-grid trap we unpack next chapter.
Go deeper: What happens when a box holds other boxes?

A slice copy copies the outer list one level deep. If the items inside are mutable lists, both outer lists still share the same inner rows:

grid = [[1, 2], [3, 4]]
shallow = grid[:]         # new outer box, shared inner boxes
shallow[0][0] = 99
print(grid)               # [[99, 2], [3, 4]]

For flat lists of numbers or strings, xs[:] and list(xs) are completely safe. When you reach 2D tables in the next chapter, you will build each inner row individually with a comprehension instead of sharing one row.

After these five lines run, what does raw hold?

raw = [12.0, 15.0, 18.0]
alias = raw
alias[0] = -1.0
copy_list = raw[:]
copy_list.append(99.0)

Spot on. alias = raw adds a sticky note to the same box, so alias[0] = -1.0 edits raw. Slicing raw[:] makes a new box, isolating 99.0.

Count boxes: line 1 makes Box A, line 2 labels Box A as alias (so line 3 edits Box A), and line 4 slices out a separate Box B for copy_list.

2How do lists, tuples, and half-open slices grab exact pieces?

Python gives you two ordered containers: a list (editable box) and a tuple (sealed box whose slots stay fixed). Small bundles unpack cleanly into named variables via tuple unpacking:

scores = [18.0, 21.5, 24.0, 19.5, 17.0]
bounds = (17.0, 24.0)

low, high = bounds        # tuple unpacking
print(low, high)          # 17.0 24.0

# bounds[0] = 15.0  -> TypeError (tuples stay fixed)
scores[0] = 19.0          # lists allow in-place updates

Slots count from 0 on the left and -1 from the right. Slicing with xs[start:end] is half-open: it includes start and stops right before end. A third step value reverses a sequence via xs[::-1]:

temps = [18.0, 21.5, 24.0, 19.5, 17.0]

print(temps[0])           # 18.0
print(temps[-1])          # 17.0
print(temps[1:4])         # [21.5, 24.0, 19.5]  (len = 4 - 1 = 3)
print(temps[0:0])         # []
print(temps[:2])          # [18.0, 21.5]
print(temps[3:])          # [19.5, 17.0]
print(temps[::-1])        # [17.0, 19.5, 24.0, 21.5, 18.0]

Picture slice indices as fenceposts sitting between items:

Count fenceposts, not items: xs[1:4] spans cut 1 to cut 4 (length 4 - 1 = 3), while xs[0:0] cuts at post 0 twice and returns [].
Half-open slicing keeps math clean: xs[start:end] has length end - start, and splitting at cut k into xs[:k] + xs[k:] stitches back with zero overlap.

Slicing a tuple returns another immutable tuple. Wrap the slice in list(...) whenever you must return a fresh editable list:

raw_tuple = (18.0, 21.5, 24.0, 19.5, 17.0)
window = list(raw_tuple[1:4])   # fresh mutable list
window[0] = -1.0

print("window:   ", window)     # [-1.0, 24.0, 19.5]
print("raw_tuple:", raw_tuple)  # (18.0, 21.5, 24.0, 19.5, 17.0)

For the tuple row = (18, 21, 24, 27, 30), what are mid, empty, and rev[0] — and what happens on mid[0] = 99?

row = (18, 21, 24, 27, 30)
mid = row[1:4]
empty = row[0:0]
rev = row[::-1]

Correct! Cut 1 to 4 gives 3 items ((21, 24, 27)), cut 0 to 0 is (), [::-1] starts at row[-1] (30), and tuple slices stay immutable until wrapped in list(...).

Check cuts and type separately: fenceposts 1..4 hold 3 items, 0..0 holds 0, step -1 starts at 30, and slicing a sealed tuple returns a tuple.

3How do functions, type hints, and ValueError guards protect your scripts?

Wrapping logic in def avoids copy-pasted loops and gives you three safeguards: a default argument for common runs, type hints documenting inputs/outputs, and a raise ValueError(...) guard that halts invalid inputs loudly:

from collections.abc import Sequence

def cap_values(vals: Sequence[float], cap: float = 100.0) -> list[float]:
    if cap < 0:
        raise ValueError("cap must be non-negative")
    out = []
    for val in vals:
        if val > cap:
            out.append(cap)
        else:
            out.append(val)
    return out

print(cap_values([45.0, 120.0, 88.0]))     # [45.0, 100.0, 88.0]
print(cap_values((45.0, 120.0), cap=90.0)) # [45.0, 90.0]

Every exercise stub in this book uses four straightforward type hints:

Type hintPlain-English meaning
Sequence[float]Any ordered collection of numbers you can loop over and slice (list or tuple).
list[float]A mutable list of floats returned fresh to the caller.
dict[str, int]A dictionary mapping string keys to integer counts.
Sequence[object]Any ordered sequence of arbitrary Python items.
Go deeper: Type hints at runtime and from __future__ import annotations

Python treats type hints as readable labels for humans and editors — not runtime bouncers. Passing -5.0 into cap: float is allowed by the hint, which is why explicit if ...: raise ValueError(...) guards still matter.

The line from __future__ import annotations at the top of every exercise stub lets Python accept built-in annotations like list[float] cleanly across Python versions.

With raw = [40.0, 130.0], you call trimmed = cap_values(raw) and then cap_values(raw, cap=-5.0). What happens?

Spot on. Omitting cap uses default 100.0, out = [] leaves raw untouched, and cap=-5.0 trips the explicit ValueError guard.

Trace three pieces: cap=100.0 is optional, appending into out = [] never mutates raw, and only the if cap < 0 guard rejects -5.0.

4How do dicts count items and sets deduplicate at 100,000-item speed?

To tally events or words, writing counts[e] = counts[e] + 1 crashes on the first sighting with KeyError: 'ok'. Calling counts.get(e, 0) returns 0 when a key is missing, and empty input [] naturally leaves {}:

events = ["ok", "retry", "ok", "timeout", "ok"]

# Naive: counts[e] = counts[e] + 1  -> KeyError: 'ok'

counts = {}
for e in events:
    counts[e] = counts.get(e, 0) + 1

print(counts)     # {'ok': 3, 'retry': 1, 'timeout': 1}

What happens below on tags = ["ok", "warn", "ok"] versus tags = []?

counts = {}
for tag in tags:
    counts[tag] += 1

Right! counts[tag] += 1 reads counts["ok"] before adding 1. Using counts.get(tag, 0) + 1 fixes first sightings while keeping {} on empty input.

Expand += 1 to counts[tag] = counts[tag] + 1: reading missing "ok" throws KeyError, whereas [] skips the loop and leaves {}.

Next, suppose you want to remove duplicates while keeping first-seen order. Two shortcuts break in opposite ways: list(set(tags)) scrambles order because Python sets do not remember insertion order, while checking if tag not in out: against a list crawls at 100,000 items.

Think of searching a list as scanning a 100,000-line unindexed notebook from line 1 downward: deduplicating 100,000 distinct items runs 100,000 × 99,999 / 2 = 4,999,950,000 checks. A set jumps straight to a labeled index tab in 1 step — 100,000 lookups total, shrinking over a second of scanning to a few milliseconds.

One limit of index tabs: only immutable values (strings, numbers, tuples) can sit in a set or serve as dict keys. Editing a mutable list key later would invalidate where it was filed, so Python forbids it up front.

Pair both containers — seen = set() for speed and out = [] for order:

tags = ["gpu", "py", "gpu", "math", "py", "data"]

# list(set(tags)) can scramble order across runs!
seen = set()
out = []
for tag in tags:
    if tag not in seen:
        seen.add(tag)
        out.append(tag)

print(out)        # ['gpu', 'py', 'math', 'data']
Pair set for speed with list for order: seen = set() checks membership in one tab lookup while out = [] preserves exact first-seen order.
Press Next (or Play) on ["red", "blue", "red", "green", "blue"]. Watch seen catch duplicates in one tab check (amber) while out keeps first-seen order.
Explain it another way: Why dict and set share the same instant lookup

A set is a dict storing only index tabs with no attached values. Both jump directly to a label instead of scanning from slot 0.

Use a dict when every label carries a value (like a count), and a set when you only need a fast yes/no membership test.

You deduplicate 100,000 distinct IDs and need first-seen order. Draft A runs list(set(ids)); Draft B checks if x not in out: on a list. What breaks?

Nailed it. Dicts keep insertion order, not sets, and scanning out runs 4,999,950,000 checks. Pairing seen = set() with out = [] avoids both traps.

Separate the jobs: set gives instant tab lookup with no order guarantee; list keeps order but scans from slot 0 — averaging ~50,000 checks per ID.

5How do zip, enumerate, and sum/min/max replace fragile index loops?

Manual counter loops like for i in range(len(a)): add noise and invite off-by-one slips. Use zip(a, b) to pair matching slots directly — while watching its sharpest trap: unequal lengths silently drop trailing items with zero error:

prices = [4.0, 2.5, 10.0]
qtys   = [2, 4]                 # missing 3rd quantity

# Silent trap: zip stops at the shorter list and drops 10.0
print(list(zip(prices, qtys)))  # [(4.0, 2), (2.5, 4)]

Whenever two sequences must match 1-to-1, guard lengths with raise ValueError(...) first, then unpack each pair in the loop header:

from collections.abc import Sequence

def line_totals(
    prices: Sequence[float], qtys: Sequence[int]
) -> list[float]:
    if len(prices) != len(qtys):
        raise ValueError("prices and qtys must have the same length")
    totals = []
    for price, qty in zip(prices, qtys):
        totals.append(price * qty)
    return totals

print(line_totals([4.0, 2.5, 10.0], [2, 4, 1]))  # [8.0, 10.0, 10.0]

Two empty lists return [], inputs stay untouched, and mismatched lengths fail loudly before any multiply runs.

Go deeper: zip(..., strict=True) in Python 3.10+

Passing strict=True makes zip raise ValueError automatically on unequal lengths:

# Python 3.10+ raises ValueError automatically with strict=True:
for price, qty in zip([4.0, 2.5, 10.0], [2, 4], strict=True):
    print(price * qty)
# ValueError: zip() argument 2 is shorter than argument 1

An upfront if len(a) != len(b): guard still helps on sequences because it fails before partial loop work and gives a clear error message.

Step Mismatched lengths (silent trap!) first: zip halts at index 2 and drops 30 and 40 with zero error. Then toggle Matching lengths (safe) to compare.

One label went missing from targets before this loop ran. What happens?

preds = [4, 7, 2, 9]
targets = [3, 5, 2]
diffs = []
for p, t in zip(preds, targets):
    diffs.append(p - t)

Exactly — default zip() stops at the shorter list with zero warning. Guard with if len(a) != len(b): raise ValueError(...) or strict=True.

Picture a zipper with 4 teeth against 3: after tooth 3 pairs, the zipper stops quietly without inventing a zero, dropping prediction 9.

When you need both 0-based position and value from one sequence, unpack enumerate(items) directly (empty or no-match inputs return []):

latencies_ms = [180, 920, 310, 860, 240]

slow_slots = []
for idx, ms in enumerate(latencies_ms):
    if ms > 800:
        slow_slots.append(idx)

print(slow_slots)  # [1, 3]

For basic totals and bounds, call Python's built-ins sum, min, and max (note that sum([]) returns 0, while min([]) and max([]) raise ValueError):

latencies_ms = [180, 920, 310, 860, 240]

print("total:", sum(latencies_ms))                      # 2510
print("best: ", min(latencies_ms))                      # 180
print("worst:", max(latencies_ms))                      # 920
print("mean: ", sum(latencies_ms) / len(latencies_ms))  # 502.0

6How do comprehensions fold loops cleanly — and when should you stop?

A list comprehension folds the recurring out = [] → for → optional if → out.append(...) loop into one bracketed expression:

latencies_ms = [180, 920, 310, 860, 240]

# Transform every item (ms -> seconds)
secs_loop = []
for ms in latencies_ms:
    secs_loop.append(ms / 1000)
secs_comp = [ms / 1000 for ms in latencies_ms]

# Filter + enumerate (slots over 800 ms)
slow_idx = [i for i, ms in enumerate(latencies_ms) if ms > 800]

print(secs_comp)   # [0.18, 0.92, 0.31, 0.86, 0.24]
print(slow_idx)    # [1, 3]
Match the three colored pills: the appended expression moves first (1. keep), followed by 2. loop and optional 3. filter.

Curly braces with key: value fold the same way into a dict comprehension:

steps = ["load", "clean", "score"]
times_ms = [12, 45, 8]

fast_loop = {}
for step, ms in zip(steps, times_ms):
    if ms < 20:
        fast_loop[step] = ms

fast = {s: ms for s, ms in zip(steps, times_ms) if ms < 20}
print(fast)        # {'load': 12, 'score': 8}

You want the 0-based indices where a score is >= 0.8. What do a and b produce?

scores = [0.4, 0.9, 0.6, 0.9]
a = [scores.index(s) for s in scores if s >= 0.8]
b = [i for i, s in enumerate(scores) if s >= 0.8]

Spot on! scores.index(0.9) always stops at the first match (1), while enumerate(scores) yields live (index, value) pairs so keeping i yields [1, 3].

Trace the second 0.9 at index 3: scores.index(0.9) rescans from 0 and hits index 1 again, whereas enumerate already tracks i = 3.

Know when NOT to use a comprehension:

  • No side effects: Never write [print(x) for x in xs] (wastes a list of Nones) — use a for loop.
  • Keep it one loop + one filter: Nested branches or error guards read clearer in a plain for loop.
  • Never delete while looping: Removing from a list during iteration shifts indices; build a new filtered list instead.

✓What to remember

  1. Assignment adds a label, not a copy: b = a puts two sticky notes on one list; copy with a[:] or list(xs[start:end]) before editing.
  2. Slices are half-open: xs[start:end] keeps start, stops before end, returns [] when start == end, and reverses via xs[::-1].
  3. dict.get(k, 0) + 1 avoids KeyError, and seen = set() + out = [] deduplicates in first-seen order without 100k list scans.
  4. Guard zip() lengths first: zip(a, b) silently drops trailing items on unequal lengths, so raise ValueError upfront.
  5. Use enumerate() for positions and comprehensions for single-pass builds, falling back to a plain for loop when multi-step logic reads clearer.
